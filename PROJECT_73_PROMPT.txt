2. NUTRITION AND METABOLIC CALCULATIONS
====================================================================

Implement (or extend the existing code into) a deterministic nutrition calculation engine.

Use the Mifflin-St Jeor equation to estimate basal metabolic rate (BMR) and calculate total daily energy expenditure (TDEE) using an editable activity factor.

Recalculate when profile information changes.

Suggested initial targets:

* Estimated maintenance calories: approximately 2,150–2,250 kcal/day
* Starting calorie target: approximately 1,800 kcal/day
* Protein: 140 g/day
* Desired weight-loss rate: approximately 0.25–0.5 kg/week
* Goal: reach approximately 73 kg without unnecessary muscle loss

Sanity check for unit tests: with the default profile (male, 30 years, 174 cm, 85.5 kg) Mifflin-St Jeor gives a BMR of about 1,798 kcal. An activity factor of 1.2 gives a TDEE of about 2,157 kcal, and 1.25 gives about 2,247 kcal. This matches the suggested maintenance range.

Note on conflicting goals: losing 12.5 kg in 12 months is about 0.24 kg/week, while a 1,800 kcal target against about 2,200 kcal maintenance predicts roughly 0.35–0.45 kg/week (goal reached in about 7–9 months). The app must show both the timeframe-based and the target-based forecast, explain the difference in plain Dutch, and let the user choose. Do not silently pick one.

These are estimates, not fixed medical truths.

The app must:

1. Calculate BMR and TDEE.
2. Recommend a reasonable calorie deficit.
3. Set protein targets appropriate for muscle preservation.
4. Set sensible fat and carbohydrate targets.
5. Include fiber and fruit/vegetable goals.
6. Forecast progress toward the target weight (extend src/lib/weightLossPlan.ts).
7. Adjust projections based on recorded weight changes.
8. Warn against excessively aggressive deficits.
9. Explain calculation assumptions in plain Dutch.
10. Allow the user to override suggested targets.

Never assume that estimated daily calorie expenditure is an exact measurement.

Use deterministic code for arithmetic, quantities, macros, and progress calculations. AI must not invent numerical values.

5. REAL PICNIC SUPERMARKET INTEGRATION
====================================================================

This is a critical feature.

Use the maintained unofficial Picnic API ecosystem:

* https://github.com/MRVDH/picnic-api (npm: picnic-api)
* https://github.com/MRVDH/picnic-mcp (npm: picnic-mcp)
* https://github.com/MRVDH/picnic-web (reference web frontend)

Re-verify the latest versions and methods when you start. Verified on 2 November 2026:

* picnic-api 5.3.0 (published 23 October 2026). It has no runtime dependencies and uses the global `fetch`, so it should run inside the existing Cloudflare Worker (nodejs_compat is already enabled). Verify this with a real Worker build before you rely on it. If it does not run on Workers, isolate it behind a small adapter so it can be swapped or run in a separate service.
* Client: `new PicnicClient({ countryCode: "NL", authKey, deviceId, ... })`.
* Auth: `auth.login(email, password)` returns `{ authKey, userId, secondFactorAuthenticationRequired }`. Then `auth.generate2FACode("SMS")` and `auth.verify2FACode(code)` returns `{ authKey }`. Also `auth.logout()`. (Note: the README example says `verify2FA`, but the actual method is `verify2FACode`.)
* Catalog: `catalog.getSearchResults(query)`, `catalog.getSuggestions(query)`, `catalog.getProduct(productId)` (price, nutrition, allergens, ingredients), `catalog.getImageUrl(imageId, size)`, `catalog.getFavorites()`, `catalog.getPromotions()`.
* Cart: `cart.getCart()`, `cart.addProductToCart(productId, count)`, `cart.removeProductFromCart(productId, count)`, `cart.clearCart()`, `cart.getReplacements(productId)`, `cart.getDeliverySlots()`, `cart.setDeliverySlot(slotId)`, `cart.getMinimumOrderValue()`. Cart mutations return the updated cart.
* Checkout: `checkout.startCheckout({ mts, resolveKey?, outOfStockArticleIds? })` (mts is the cart's modification timestamp; checkout fails when the cart changed since, so use this as a safety check). Then `checkout.initiatePayment(orderId, appReturnUrl)` returns a payment redirect / issuer authentication URL, followed by `checkout.getCheckoutStatus(transactionId)`, `checkout.confirmOrder(orderId)`, `checkout.getOrderStatus(orderId)` and `checkout.cancelCheckout(transactionId)`. Blocking issues (for example age verification) come back as `CheckoutIssueError`.
* Errors: `PicnicApiError`, `CheckoutIssueError`, `UnexpectedPageFormatError`, `ProductNotFoundError`. Handle each one explicitly.
* picnic-mcp 1.0.0 states explicitly that it "can't place an order". Do not assume MCP can complete checkout. Use picnic-api directly in the backend. picnic-mcp is useful as a reference for compact product matching (bestMatch / choices) and for privacy-conscious output.

The Picnic integration must run exclusively through the secure backend (the existing Worker).

Never expose authentication secrets or Picnic auth keys to frontend JavaScript.

For every required ingredient:

* Determine suitable product matches.

Never invent Picnic products, stock status, identifiers, or prices.

Cache product lookups briefly and server-side, and show when the data was retrieved.

Example:

The meal plan requires 450 grams of chicken across three meals.

Picnic sells a 500-gram package.

The app should recognize that one 500-gram package covers the requirement.

Do not add three separate chicken packages.

Apply the same logic to all groceries.

Use explicit package quantities, edible amounts, and units.

Handle:

* Grams
* Kilograms

The user should see an overview of:

Investigate whether the picnic-api checkout methods listed above can be implemented reliably and safely for the user's account.

If supported and explicitly enabled (server flag PICNIC_CHECKOUT_ENABLED, off by default, plus a user setting), implement checkout through the backend with:

====================================================================

This is a major differentiating feature.

Do not simply generate recipes and add ingredients.

The application should intelligently optimize the combination of meals and supermarket products.

Example:

The AI generates seven meals requiring 12 different ingredients.

However, the supermarket only sells certain products in larger packages.

Build an optimization workflow:

1. Generate candidate meals.
2. Aggregate required ingredients.
3. Find real purchasable products.
4. Calculate package quantities and estimated cost.
5. Identify surplus ingredients.
6. Suggest compatible ingredient reuse or meal substitutions.
7. Recalculate nutrition.
8. Choose a practical plan.
9. Present it for approval.

The objective is to produce an affordable, realistic grocery basket while preserving nutritional requirements.

Support a configurable grocery budget and maximum preparation time.

Distinguish the cost of purchased groceries from the estimated cost of consumed portions. Surplus from one plan should flow into the pantry for the next plan.

14. PRIMARY USER JOURNEY (ACCEPTANCE TEST)
====================================================================

Implement and test this complete scenario.

Starting state

User:

* Weighs 85.5 kg
* Wants to reach 73 kg
* Targets approximately 1,800 kcal daily
* Targets 140 g protein daily
* Lives alone
* Prefers little cooking
* Wants three days of food

Action 1

User clicks: "Plan mijn maaltijden"

Expected: the app calculates nutritional targets and creates a complete three-day meal plan.

Action 2

User clicks: "Zoek boodschappen bij Picnic" (same action as "Bereid boodschappen voor" on the dashboard)

Expected: the backend searches actual Picnic products, matches meal ingredients, calculates package quantities, checks availability and prepares the shopping list.

Action 3

User reviews the basket.

Expected: the app displays real product names, prices and quantities. The user can make substitutions and see the updated total.

Action 4

User clicks: "Vul mijn Picnic-winkelmandje"

Expected: the real Picnic cart is synchronized successfully without duplicates or unwanted removal of existing items. Pressing the button twice does not change the result.

Action 5

User selects a delivery slot and approves checkout.

Expected: if supported and configured, proceed with explicit approval and verify order confirmation. Otherwise provide a clearly labeled official Picnic handoff.

Action 6

User eats meals ("Gegeten") and records a new weight one week later.

Expected: the progress dashboard updates and the coaching engine reassesses progress.

Additional acceptance check for the existing app: an account with existing Project 75 data (weights, food logs, workouts, photos) opens after the upgrade with all data intact and the goal moved to 73 kg.

This complete workflow is the primary acceptance test.

15. DEVELOPMENT EXECUTION REQUIREMENTS
====================================================================

Important: Do not stop after generating a project plan.

Actually build and wire the application.

Development sequence:

Phase 0: Orientation and safety net

Read the existing code. Make sure build, lint and tests pass before changing anything. Write a short architecture note (docs/project-73-architecture.md) covering how the new modules fit into the existing ones.

Phase 1: Functional foundation

Rebrand to Project 73, Dutch UI, new 5-page navigation, profile extension and migration (75 → 73 kg), Mifflin-St Jeor / TDEE engine, weight logging and trend, and the new dashboard.

Phase 2: Meal planning

Actual meal plan generation (deterministic templates first, AI on top), verified nutrition calculations, recipe management, portion adjustments, "Gegeten" tracking, favorites and reuse.

Phase 3: Grocery optimization

Pantry, ingredient consolidation, unit conversion, package-aware quantity calculations, product matching against the mock adapter, and grocery cost optimization.

Phase 4: Picnic integration

Encrypted account connection with 2FA, real product search, real prices, cart diff and idempotent sync, delivery slots, and safe checkout behind the flag or the official Picnic handoff.

Phase 5: AI assistant

Tool-calling assistant with Zod-validated structured output, confirmation of changes, and deterministic fallback.

Phase 6: Quality assurance

Test complete user workflows.

Include Vitest unit tests for:

* Metabolic calculations (BMR/TDEE fixture from section 2)
* Macro calculations
* Recipe portion scaling
* Ingredient unit conversion
* Grocery quantity consolidation
* Package rounding (450 g needed + 500 g package = 1 package)
* Shopping cart idempotency
* Cart diffing (never removing unrelated items)
* Weight-trend calculations
* Data migration from the existing Project 75 payload

Include integration tests using mocked Picnic responses (shaped like real picnic-api 5.x types), an end-to-end test of the primary journey (Playwright) against the mock adapter, plus a clearly documented manual live integration test.

Do not send real orders during automated tests. Live tests must never call checkout.

Provide:

* Complete source code in this repository
* Working development environment (pnpm dev with local D1)
* Updated .env.example
* Database schema and migrations
* Updated README (rename to Project 73)
* Setup instructions
* Configuration instructions for Picnic
* Configuration instructions for the AI provider
* Deployment guidance (Sites / Cloudflare, secrets, migrations)
* An explicit list of features that require real account credentials or manual verification

Whenever an integration cannot be completed, clearly document the limitation and provide a functional alternative.

Do not pretend unfinished functionality works.

Commit in logical steps per phase with clear messages.

16. DEFINITION OF DONE
====================================================================

The app is successful when the user can:

1. Open a polished, Dutch frontend branded Project 73.
2. View their personal weight-loss target (73 kg) and nutrition needs.
3. Generate three days of meals.
4. Edit or replace meals.
5. See accurate planned calories and protein.
6. Convert meal ingredients into a consolidated grocery list.
7. Match ingredients to actual available Picnic products.
8. See real package quantities and prices.
9. Review and synchronize the shopping cart.
10. Approve checkout or continue safely in Picnic.
11. Log their weight and see progress over time.
12. Reuse the application three days later without repeating setup.
13. Still use all existing data and features (workouts, FitDays, photos, backups) without loss.

Final priority

Focus on the real end-to-end user journey.

A simple application that reliably plans meals and prepares a real Picnic order is significantly more valuable than a beautiful interface full of simulated functionality.

Make reasonable engineering decisions autonomously, work through implementation problems, and complete as much of the working application as possible.
